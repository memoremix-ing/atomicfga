Part 1 · Fine-grained authorization

1. The authorization question

Authentication establishes who you are. Authorization answers a different question, asked thousands of times a second in a busy application:

Can user:anne do can_view on doc:plan?

Three broad families of systems answer it:

Google described its ReBAC system, Zanzibar, in a 2019 paper; it answers authorization for Drive, YouTube, Calendar and more. OpenFGA is an open-source system in that style (a CNCF project started at Auth0/Okta). Two ideas carry over from Zanzibar:

  1. Relationships are data. “anne is a member of eng” is a row, written when it becomes true.
  2. Rules are a model. “viewers of a folder can view its documents” is written once, separately, and applies to all those rows.

2. Objects, relations, users, tuples

Everything in OpenFGA is described with four words:

  • Object — a thing with a type and an ID: doc:plan, folder:q3, group:eng.
  • Relation — a named link an object can have: viewer, member, parent.
  • User — whatever sits on the other end: a concrete user:anne, a whole set of users written as group:eng#member (“every member of eng”, a userset), everyone of a type user:* (a wildcard), or even another object (folder:q3).
  • Tuple — one stored fact: user has relation to object.

A store holds one set of tuples plus that set’s models. Stores are fully separate from each other; in a multi-tenant system, one store per tenant is the natural layout.

3. The authorization model

The model declares the types, which relations each type has, and — most importantly — how a relation can be derived from other relations. OpenFGA has a readable DSL; the canonical form, and the one atomicfga accepts, is the equivalent JSON (WriteAuthorizationModelRequest). The DSL is shown here because it is easier to read:

model
  schema 1.1

type user

type group
  relations
    define member: [user]

type folder
  relations
    define owner:  [user]
    define viewer: [user, group#member] or owner

type doc
  relations
    define parent:   [folder]
    define owner:    [user]
    define editor:   [user] or owner
    define viewer:   [user, user:*] or editor or viewer from parent
    define blocked:  [user]
    define can_view: viewer but not blocked

Each define is built from a few operators:

Direct — [user, group#member]

True if a tuple says so. The brackets list which kinds of users such tuples may name; writes that name anything else are rejected.

Computed — or owner

“Every owner is also an editor.” Same object, different relation.

Tuple-to-userset — viewer from parent

“Follow this object’s parent tuples, and ask the parent about viewer.” This is how permissions flow down hierarchies.

Set algebra — or, and, but not

Union, intersection, exclusion. can_view above is “viewer, except the blocked”.

Conditions refine a direct relation with a small CEL expression evaluated at check time, e.g. [user with office_hours]. Note where its inputs come from — the condition’s parameters are filled from the tuple and from the request’s context, so a time-based rule receives the time from the caller, not from the server’s clock. Conditions do not make a Check depend on server time.

4. How a Check is answered

A Check is a search: starting from the requested relation, expand the model’s rule into sub-questions, read the tuples each one needs, and stop as soon as the answer is settled. Choose a user to walk through Check(user, can_view, doc:plan):

Other API calls are variations on the same search: ListObjects (“which docs can anne view?”), ListUsers (“who can view plan?”), Expand (show the tree). Write adds and deletes tuples; Read lists them; ReadChanges is a feed of tuple writes and deletes, in order, for syncing other systems.

5. Models are versioned

Since the answer depends on the model, changing the model is a big deal. OpenFGA never edits a model: writing one adds a new version with a fresh ID, and old versions stay readable forever. Tuples are not tied to any version — the same rows are reinterpreted by whichever model a request uses.

Part 2 · atomicfga

6. What atomicfga changes

A normal OpenFGA deployment is a separate server with its own database. Your application writes its own rows to its database and, separately, tells OpenFGA about relationships. Those are two commits; between them — or if one fails — the two systems disagree. atomicfga runs unmodified OpenFGA code inside your application’s SQL transaction, against OpenFGA’s tables living in your database.

In code (Go), the shape is: open your transaction, wrap it, call OpenFGA’s API on the wrapper:

tx, _ := db.BeginTx(ctx, nil)
fga := engine.Session(atomicfga.SQLTx(tx))

tx.ExecContext(ctx, `INSERT INTO orders ...`)
fga.Write(ctx, &openfgav1.WriteRequest{StoreId: store, Writes: ...})
resp, _ := fga.Check(ctx, &openfgav1.CheckRequest{StoreId: store, TupleKey: ...})

tx.Commit() // both, or (Rollback) neither

The data lives in OpenFGA’s own tables in your database. Every one of them is keyed by store first, which is what makes a store (a tenant) a clean, movable slice:

The Rust port (the evaluator that also runs in browsers) keeps only two tables — tuples keyed (store, object, relation, user) and models keyed (store, model ID) — and has no change feed. It never reads the clock: the caller supplies model IDs.

Part 3 · Clocks

7. ULIDs: IDs with a clock inside

OpenFGA names stores, models, tuples and changelog entries with ULIDs: 128-bit IDs written as 26 characters. The first 48 bits are the current time in milliseconds; the remaining 80 bits are random.

This is a reasonable design for unique IDs: no coordination, roughly time-ordered, index-friendly. The trouble starts when the order of IDs is given a meaning — “greatest = newest” — because then correctness depends on every machine that mints IDs agreeing about the time.

Within one process, OpenFGA’s ULID library keeps IDs minted in the same millisecond increasing. Across processes, across machines, or after a machine’s clock is stepped backwards, nothing does.

Both exist in any upstream OpenFGA deployment with more than one server — atomicfga inherits them rather than adding them, and moving tenants between servers makes them more likely to bite.

Part 4 · Model ID handling

11. Fix: choose the model by data, not by time

The principle: which model applies should be a fact your transaction reads, not an inference from timestamps. atomicfga makes this cheap, because your own tables share the transaction with OpenFGA’s.

Option 1 — a model pointer in your schema

// Deploy a model: the new rules and the switch to them commit together.
tx, _ := db.BeginTx(ctx, nil)
fga := engine.Session(atomicfga.SQLTx(tx))
m, err := fga.WriteAuthorizationModel(ctx, &openfgav1.WriteAuthorizationModelRequest{
    StoreId: store, SchemaVersion: "1.1", TypeDefinitions: types,
})
_, err = tx.ExecContext(ctx, `
    INSERT INTO authz_model_pointer (store_id, model_id) VALUES (?, ?)
    ON CONFLICT (store_id) DO UPDATE SET model_id = excluded.model_id`,
    store, m.GetAuthorizationModelId())
tx.Commit()

// Any request: the pointer is read in the same transaction as everything else.
var model string
tx.QueryRowContext(ctx, `SELECT model_id FROM authz_model_pointer WHERE store_id = ?`, store).Scan(&model)
resp, err := fga.Check(ctx, &openfgav1.CheckRequest{
    StoreId: store, AuthorizationModelId: model, TupleKey: key,
})

SQLite placeholders shown; use $1, $2 on Postgres. Pass the same ID to Write, ListObjects and the rest: Write validates tuples against a model too.

Cost: one indexed read per transaction (reuse it for every call in that transaction). atomicfga already queries the model table on every request either way — for “latest” when no ID is given, or to confirm the named ID is visible in your transaction — so the extra work is small. OpenFGA’s own documentation also recommends passing a model ID in production.

Option 2 — every request names its model always on

Option 1 is a convention, and conventions get forgotten: one call without an ID would silently fall back to “latest”. So atomicfga refuses every request that uses a model but names none — Check, BatchCheck, Expand, ListObjects, StreamedListObjects, ListUsers, Write, RustCheck — with ErrModelIDRequired (InvalidArgument). There is no setting to turn it off: the convention is a guarantee, the pit of success. The Rust API and the browser evaluator answer such requests with invalid_argument.

_, err = fga.Check(ctx, &openfgav1.CheckRequest{StoreId: store, TupleKey: key})
errors.Is(err, atomicfga.ErrModelIDRequired) // true: name the model

Option 3 — model IDs only go up implemented

The model written last always ranks first. In Go, where OpenFGA mints the ID, atomicfga reads the store’s greatest model ID in the write’s transaction; if the freshly minted ID is not above it (the clock is behind), the model is stored under the greatest ID’s millisecond plus one, with fresh random bits, and the response names that ID. Nothing fails, and nothing is hidden: the response always tells you the ID. On PostgreSQL, model writes to one store also take a transaction-scoped advisory lock, so two transactions writing models to the same store rank in commit order (at READ COMMITTED, the default). In the Rust port the caller supplies the ID, so a non-increasing one is refused with invalid_argument before anything is written. With options 1 and 2 in place this is defence in depth, and it keeps “latest”, ReadAuthorizationModels order and any tooling that reads them honest.

Result: you keep Option 1 in your schema; atomicfga enforces Option 2 and Option 3. Together they make the clock irrelevant to which rules a Check applies.

Appendix

A. Other authorization systems, for multi-tenant placement

For moving tenants around, three properties matter: all authorization state is keyed by tenant; none of it lives only on one server; and nothing orders it by wall clock. atomicfga has the first two and, with §11, the third for model selection. Systems that store nothing get these trivially — because your relationship data becomes ordinary app tables — so the real differences lie elsewhere:

gatehouse is an in-process policy library: policies are async Rust (RBAC, attribute predicates, relationship checks), deny overrides allow, and facts come from sources you implement, batched and cached per request. It stores nothing and reads no clock, so it is trivially “placement friendly” — but only because your relationship data and its traversal become your problem, and rules can’t differ per tenant without you building that. Cedar is the strongest choice if mechanical verifiability of the rules is paramount and your relationships are shallow enough to hand in with each request. SpiceDB is a Zanzibar-style service like upstream OpenFGA, so it reintroduces the two-commit problem atomicfga exists to remove.

B. Glossary

Store
An isolated set of tuples and models. One per tenant is the natural multi-tenant layout.
Authorization model
Types, relations and rewrite rules. Immutable; each write creates a new version with a new ID.
Tuple
One stored relationship: user has relation to object, optionally with a condition.
Userset
A set of users named by an object and relation, e.g. group:eng#member.
Tuple-to-userset
A rule that follows a relation to another object and asks it a question: viewer from parent.
Check
“Does user U have relation R on object O?” — a search over the model and tuples.
Latest model
The model a request uses when it names none: in OpenFGA, the greatest model ID.
ULID
A 128-bit ID: 48 bits of millisecond timestamp, 80 random bits; sorts by its minting clock.
Changelog / ReadChanges
The ordered history of tuple writes and deletes, and the API that pages through it with a continuation token.
Horizon offset
ReadChanges hides entries younger than this, giving in-flight transactions time to commit.
Model pointer
A row in your schema naming the model a store uses; chosen in a transaction, not by time.
